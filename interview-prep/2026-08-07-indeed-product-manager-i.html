Indeed: Product Manager I

Prepared answer: experimentationPrepared 7 August 2026Two-sided marketplace

Why this question

The JD says "launch features rapidly using data-driven testing and validation". It lists a "data-driven approach with deep curiosity about product metrics" as a required qualification. Indeed runs experiments at very large scale. Some version of "tell me about an experiment you ran" is close to certain.

Where I stand

I have strong before-and-after measurement and real instrumentation. I have not run a formal A/B test with a randomised control group, a pre-registered primary metric and a significance calculation. On regulated payment rails, live money flows are not split-tested.

The structure of the answer

  1. Name the boundary first. "I should be straight that most of my measurement has been pre-post and cohort-based. I have not run randomised controlled tests. Here is what I have done."
  2. Give the strongest true example, with numbers.
  3. Show what the real thing requires. Name the machinery I would use at Indeed's scale, and the part that is hardest in a marketplace.

Three true examples

1. NPS on Bharat Connect: the authentication change

  • Hypothesis: the 12-digit PRAN entry was the drop-off point in the contribution flow.
  • Change: replaced it with mobile-number-linked authentication, reaching a 5-click contribution path.
  • Framing: a funnel hypothesis validated by shipping, without a holdout group.

2. Biller Analytics: validation before build

  • Ran discovery with billers to decide which metrics they would act on, before anything was built. That is qualitative validation, and a fair answer to "how do you validate".
  • Then measured adoption: ~50K MAU, ~30-minute sessions, and downloads from 100 in month 1 to ~15,000 by month 12.
  • Self-critique: downloads are an activity metric. The value metric is whether a biller changed a decision because of the dashboard. That is what I would want to measure at Indeed.

3. Agent Locator: leading and lagging indicators

  • Leading: monthly searches from 1,000 to ~200,000 in four months.
  • Lagging: complaints about uncertified collectors fell from ~200 a month to near zero. Remote cash-deposit TAT fell from 4 days to 8 hours.
  • The point: the search number is close to a vanity metric. The complaint drop shows the product worked. Choosing it as the headline is the signal.

Experimentation vocabulary

  • Randomisation unit. User, session or account. At Indeed a job seeker sees many jobs, so randomising per search result leaks. Usually you randomise per user.
  • Primary metric and guardrail metrics. One metric you are trying to move, plus a set you must not break, such as application completion rate, employer satisfaction and latency.
  • Minimum detectable effect and power. The size of effect you care about sets the sample size and the runtime. This is how you answer "how long should we run it?"
  • Peeking. Checking results daily and stopping when it looks significant inflates false positives. Fix the runtime in advance, or use a sequential test designed for it.
  • Novelty and primacy effects. New things get clicked because they are new. Short tests overstate the win.
  • Interference in two-sided marketplaces. Lead with this one. If treated seekers see better-matched jobs, they apply to and fill roles that control seekers would have filled. Treatment and control then affect each other, so a naive A/B test overstates the effect. Remedies include cluster randomisation by geography or job category, and switchback testing over time windows. Indeed lives with this problem every day. The point comes straight from having built on a two-sided network.
  • Offline and online evaluation. This ties to LLM work. An offline eval set tells you whether a model output is good. An online test tells you whether users behave differently. Both are needed, and they often disagree.

The line to say

"I want to be accurate about this. I have not run formal randomised A/B tests with pre-registered metrics and power calculations. What I have done is define the success metric before the build, instrument it, and measure the outcome that matters. At Indeed's scale I would expect to work inside an existing experimentation platform. The part I would want to get right early is interference, because on a two-sided marketplace, treating one side changes the supply available to the control group."
